# Todo App (Next.js + FastAPI)

Next.js App Router와 FastAPI를 분리한 구조로 Todo 앱을 마이그레이션하기 위한 프로젝트입니다.  
프론트엔드는 화면과 사용자 인터랙션을 담당하고, 백엔드는 Todo 데이터를 관리하는 역할로 나눕니다.

---

## 3차 과제 기능 분리 정리

### 프론트엔드(Next.js)
- Todo 목록, 생성, 수정, 삭제 화면 렌더링
- `/todos`, `/todos/new`, `/todos/[todoId]` 페이지 구성
- Server Actions 또는 API Route를 통한 데이터 요청
- 로딩, 에러, 빈 상태 UI 처리
- 입력 폼과 버튼 클릭 이벤트 처리
- 화면 이동과 라우팅 처리

### 백엔드(FastAPI)
- Todo 데이터 저장, 조회, 수정, 삭제 API 제공
- 요청 데이터 검증
- 프론트엔드에서 전달한 CRUD 요청 처리
- 서버 상태 관리와 응답 포맷 구성

### 2차 과제에서 역할이 바뀌는 부분
- `localStorage` 저장/복원 -> FastAPI 서버 저장/조회
- 프론트 상태 관리 중심 CRUD -> 서버 요청 기반 CRUD
- 날짜/필터 화면 렌더링 -> 프론트 유지
- 데이터 영속성 책임 -> 백엔드로 이동

- **프론트엔드 프로젝트 세팅**
  - `frontend/` 디렉토리에서 Next.js 프로젝트를 실행할 수 있도록 기본 의존성을 설치함
  - `app/` 기반 App Router 구조가 보이도록 `layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx` 등의 기본 파일을 생성함
  - `localhost:3000`에서 확인할 수 있는 기본 화면이 뜨도록 초기 구조를 정리함
- **백엔드 프로젝트 세팅**
  - `backend/` 디렉토리에서 FastAPI 실행을 위한 가상환경(`.venv`)을 생성함
  - `requirements.txt`를 기준으로 FastAPI, Uvicorn, python-dotenv 등의 패키지를 설치함
  - `main.py`에 FastAPI 앱의 최소 진입점을 만들어 `localhost:8000`에서 서버를 시작할 수 있게 구성함
  - `todos.db` 파일이 `backend/` 디렉토리에 생성되고, SQLite 테이블도 정상적으로 만들어지는 것을 확인함
  - `GET /health` 응답과 `GET /docs` Swagger UI가 정상적으로 열리는 것을 확인함
- **프론트/백엔드 역할 분리**
  - 프론트엔드는 화면 렌더링과 사용자 인터랙션을 담당하고, 백엔드는 Todo 데이터를 관리하는 구조로 역할을 나눔
  - 2차 과제에서 `localStorage`로 처리하던 데이터 저장 책임을 백엔드로 넘기는 방향을 기준으로 정리함

### 알게된 부분
- **프론트와 백엔드를 분리하면 구조가 명확해진다**
  - 화면 로직과 데이터 저장 로직이 분리되어 이후 기능을 넣을 때 기준이 훨씬 분명해졌다.
- **프로젝트 초기 세팅이 이후 구현의 기준이 된다**
  - 디렉토리 구조와 기본 파일을 먼저 맞춰두면, 다음 커밋에서 기능을 넣을 때 혼동이 줄어든다.
- **2차 과제의 역할을 다시 분배해야 한다**
  - 기존에는 프론트가 `localStorage`로 데이터를 관리했지만, 이번에는 FastAPI가 데이터를 담당하도록 책임을 나눠야 했다.
- **실행 확인이 곧 구조 검증이다**
  - `localhost:8000`의 `/health`와 `/docs`가 정상 동작하고, `todos.db`가 생성되는 것을 확인하면서 백엔드 초기 세팅이 제대로 연결됐는지 검증할 수 있었다.

## 3차 과제. 두 번째 커밋

### 구현한 부분
- **FastAPI Todo CRUD API 구현**
  - `GET /todos`로 전체 Todo 목록을 조회할 수 있도록 구현함
  - `POST /todos`로 새 Todo를 생성할 수 있도록 구현함
  - `PUT /todos/{todo_id}`로 Todo의 텍스트와 완료 상태를 수정할 수 있도록 구현함
  - `DELETE /todos/{todo_id}`로 Todo를 삭제할 수 있도록 구현함
- **SQLite 데이터 저장 연동**
  - SQLAlchemy를 사용해 `todos.db` 파일에 데이터를 저장하도록 구성함
  - `Todo` 모델과 `TodoCreate` / `TodoUpdate` / `TodoResponse` 스키마를 분리해 요청/응답 구조를 명확히 함
- **서버 실행 및 응답 확인**
  - FastAPI 서버가 정상적으로 실행되고, `/health`와 `/docs`에서 API 상태를 확인함
  - 실제로 Todo를 생성하면 DB에 반영되고, 조회 시 목록에 포함되는 흐름을 확인함

### 알게된 부분
- **백엔드는 데이터의 출처를 하나로 모으는 역할을 한다**
  - 2차 과제에서 프론트가 담당하던 저장 책임이 FastAPI와 SQLite로 이동하면서, 데이터의 기준이 하나로 정리되었다.
- **요청 스키마와 응답 스키마를 분리하는 것이 중요하다**
  - 생성/수정/조회에 필요한 데이터 형태가 다르기 때문에, Pydantic 스키마를 나눠서 관리하는 편이 더 명확했다.
- **API는 실제 동작 확인이 중요하다**
  - 단순히 코드가 작성되어 있는 것보다, `/docs`와 실제 CRUD 호출 결과가 기대대로 나오는지 확인하는 과정이 필요했다.

### AI의 도움을 받은 부분
- **AI 활용 내용 :**
  FastAPI, SQLAlchemy, Pydantic을 사용한 Todo CRUD API의 기본 구조와 엔드포인트 패턴을 참고했습니다.
- **직접 수정한 부분 :**
  DB 모델, 요청/응답 스키마, CRUD 동작 순서, 예외 처리 등을 직접 맞춰가며 과제 요구사항에 맞게 구현했습니다.
- **수정 이유 :**
  프론트가 더 이상 데이터를 직접 저장하지 않기 때문에, 서버가 Todo 데이터를 안정적으로 관리하는 구조를 먼저 완성해야 했기 때문입니다.

- **파일 위치가 곧 라우팅이 된다**

  - 데이터 요청 중이나 실패했을 때 보여줄 화면을 따로 분리해두면 사용자 경험이 더 명확해진다.

### AI의 도움을 받은 부분

- **직접 수정한 부분 :**

  - 삭제 후에도 원래 목록 주소로 돌아가도록 `returnTo` 값을 전달해 처리함

  - `app/actions.ts`에서 목록 조회, 생성, 수정, 삭제용 Server Action을 유지함
  - `app/api/todos/route.ts`는 프록시 역할로 FastAPI와 연결되는 API Route로 남겨둠
  - 과제 요구사항에 맞게 Server Action과 API Route를 함께 사용하는 구조를 정리함

### 알게된 부분
- **날짜와 필터는 렌더링 조건이다**
  - Todo 데이터를 새로 만들기보다, 쿼리와 상태를 기준으로 화면에 어떤 목록을 보여줄지 계산하는 방식이 더 자연스러웠다.

  - 생성/수정/삭제 후 같은 페이지에 머무르면 사용자가 저장이 끝난 건지 헷갈릴 수 있어서, 목록 페이지로 돌아가게 하는 처리가 필요했다.
- **route.ts와 actions.ts를 함께 쓰는 이유를 이해했다**
  - `route.ts`는 API 경로를 외부에 열어주는 통로이고, `actions.ts`는 페이지 내부에서 직접 호출하는 서버 로직이라는 점을 실제로 구분해서 보게 되었다.

### AI의 도움을 받은 부분
- **AI 활용 내용 :**
  Next.js App Router에서 날짜별 목록 렌더링, 필터 쿼리 처리, Server Action과 API Route를 함께 사용하는 구조를 참고했습니다.
- **직접 수정한 부분 :**
  생성/수정/삭제 후의 `redirect()` 흐름과 `returnTo` 전달 방식, 날짜별 목록과 필터 상태를 연결하는 로직은 직접 맞춰가며 수정했습니다.
- **수정 이유 :**
  날짜별로 Todo를 확인하고 저장 후 바로 목록으로 돌아오는 흐름이 있어야 사용자가 상태 변화를 쉽게 인지할 수 있다고 판단했기 때문입니다.
